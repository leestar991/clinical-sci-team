# patient-separator 故障档案

`SKILL.md` 与 `aggregate-ocr.md` 是聚合阶段的高频上下文。故障叙述对**理解**规则有用，

⛔ **本文件不含任何新规则**。规则以 `SKILL.md` / `aggregate-ocr.md` 为准；
两处冲突时以规则文件为准并订正本文件。

## 来源标注整体缺失

**症状**（thread `1fee1395`）：7 页 OCR **一行来源标注都没有**。`parse_image_batch` 接管落盘后
无人写「来源图片」行，而聚合侧的 `.md` 分支是**原样拼接**——于是聚合出的 `ocr_records.md`
没有页块。

**后果**：该会话判定产物里 `screenshot_ref` / `page` 出现 **0** 次
（同技能版本的 thread `9a83ccc9` 为 78 / 54）。判定语义可能是对的，但**每一条证据都不可回溯**。

**为什么没被发现**：规范与执行者不一致时，静默丢的是**可追溯性**，而没有任何闸会报错——
结构闸看的是字段在不在，不是 `page` 有没有真值。

**对应规则**：`aggregate-ocr.md`「页块结构」——`.md` 分支要求上游已写好「来源图片」行；
只有 `.txt` 回退分支（该页从未进过 `ocr/`）才由拼接侧合成。

## 页码索引落盘即丢

**症状**（会话 `09eeaffb`）：页边界在拼接时是**已知的**，但没有落盘。判定子代理只能自己
一轮轮 `grep` 重建：IN 轨把 7,604 行的 `筛选期检查/ocr_records.md` `read_file` 了 **34 次**
（整份重读 23 次；请求区间 15,068 行里 10,326 行重复 = 69%），直到第 **143** 个 AI 回合才
grep 拼出页表（`page_001: 1-377 / page_003: 739-1151…`）——**而那张表与
`ocr_page_index.py` 的输出逐行相同**。

**代价不在单次读的字节**：每次读进来的正文会被后续每一轮重新继承，把 `tokens_before`
推过压缩线 → 任务内反复压缩 26 次 → 撞 `recursion_limit`、**零产物**。

**对应规则**：`aggregate-ocr.md`「聚合后必建页码索引（⛔ 硬步骤）」——
拼接完成后立刻跑 `ocr_page_index.py`，`start_line`/`end_line` 是 1-based 闭区间，
与 `read_file` 的行区间参数同一口径，下游照抄即可。
