# QC 后修订（按轨；**一律委派修订子代理**，主代理不得亲做）

> 本文件是「拿到 `criteria_qc_{TRACK}.json` 之后怎么改 `criteria_parsed_{TRACK}.json`」的唯一权威。
> QC 怎么查见 `criteria-qc-checklist.md`；本文件只管**改**。
>
> 修订是本技能中**直接改写已落盘语义数据**的唯一步骤，也是最容易静默丢条目的一步：
> QC 要求的合并本身就会让条数下降，所以**总条数对不上无法用来发现丢条**（历史故障
> thread `5d987e97`，见文末故障档案）。因此本文件的核心是两个机械闸：
> **修订前的结构对齐闸** 与 **修订后的条数守恒记账闸**——无论谁执行修订，这两个闸都由**主代理**把守。

## 并行性（三轨互不阻塞）

IN 轨修订、EX 轨修订、OCR 子任务**三者完全并行**，彼此没有任何数据依赖：

- IN 轨与 EX 轨改的是两个不同文件（`criteria_parsed_IN.json` / `criteria_parsed_EX.json`），
  条件ID 前缀不重叠，改动不可能互相覆盖。
- OCR 走的是 `workspace/images/` → `workspace/ocr/`，与标准解析产物零交集。
- 所以：**某轨在修订时，另一轨可以继续 QC 或修订，OCR 子任务照常在途**。
  一轨达轮次上限暂停也**不阻塞**另一轨与 OCR 继续跑（是否推进到下一 Phase 由编排层按原则 7 决定）。

修订**一律委派子代理**（见下方「执行者」），它占该轨原有的那 1 个 `task` 槽位；
主代理在等待子任务返回期间必须同轮推进本地工作（跑脚本、读 QC 报告、准备下一批派发），
不得空等。

⛔ 反例（禁止）：把 OCR 全部跑完再回头修标准，或修订期间不派新 OCR 子任务。

## 修订前置闸 —— 第一层结构必须先对齐清零

⛔ **`描述索引` 与 `四分类` 双向对齐是进入语义 QC 与修订的硬前置**，不是可选检查。

两者不一致时，语义 QC 会把结构噪声当成语义问题报出来（例如「描述索引有 EX-7 但四分类没有」
被记为覆盖完整性阻断项），白白吃掉本轨仅有的 3 轮 QC 配额之一。

**典型不一致形态**：解析子代理在 `四分类` 用子条件粒度（`EX-4-1/-2/-3`）而在 `描述索引`
用父条粒度（`EX-4`），形成两套 ID 体系。

**对齐方向（唯一正确方向）**：以 `四分类` 的实体条目为准，把 `描述索引` 补齐/删改到与实体一一对应。
⛔ **禁止**反向操作——为了让索引对上而去删改 `四分类` 的实体条目或退回拆分粒度。
拆分粒度只能由语义 QC 的 `blocking_issues` 驱动改变，不能由索引对齐驱动。

**机械自检 —— 一律用技能脚本，禁止现写内联 python**：

```bash
# 解析产出后 / 每轮语义 QC 之前（省略 --track 则两轨都查）
python3 /mnt/skills/custom/criteria-parser/scripts/check_track_structure.py \
    --workspace /mnt/user-data/workspace
```

脚本跑 11 个闸（顶层结构 / 条件ID 唯一 / 前缀与轨一致 / 子序号规范 / 描述索引双向对齐 /
**原条号全覆盖** / **QC 目标实体存在** / **QC 原地打转探测** / **原文忠实性** /
**上游问题中性化** / **`或组` 语义**），完整判据见脚本 docstring。
每次运行还会落盘 `criteria_structure_gate_{TRACK}.json`（`exit_code` + 内容哈希），
QC 子代理开工前会读它并在未过闸时自行拒工。
⛔ **exit 2 时禁止发 `task(quality-control)`，禁止进入收尾。**
⛔ 脚本与 `task(quality-control)` **不得同轮发出**——同轮意味着结构结论还没回来语义 QC 就已经在跑，
前置闸等于没有（历史故障 thread `5d987e97`）。

⛔ **禁止用内联 bash/python 重写这些检查**：口径每次现写就会漂移，这正是把它收敛成脚本的原因。
需要新的检查项时改脚本，不要在会话里另写一份。

### 闸9 失配的处置（`原文失配定位`）

闸9 报失配时，报告里的 `原文失配定位` 已经给出**改哪个字符**级别的信息，逐条含四项：

| 字段 | 含义 | 怎么用 |
|---|---|---|
| `首个失配偏移` | 归一化后从头连续对上的字符数 | 定位到 `原文` 的第几个字开始偏 |
| `最长匹配前缀` | 对上的那一段（末 40 字） | 确认位置对得上 |
| `失配处` | 从失配点起的 24 字 | 看清是哪几个字不一样 |
| `raw最相近片段` | raw 中最长公共片段的邻域 | **直接照抄这里的原字符** |
| `建议` | 三类动作之一 | 见下 |

三类 `建议` 对应三种处置，⛔ **不要混用**：

1. **「照抄原字符」**（`raw最相近片段` 非空）→ 把 `原文` 改成 raw 里的写法，含标点与全半角。
   闸9 已折叠视觉等价差异（`·` 间隔号族、`–—‐～` 破折号族、零宽字符、中英引号），所以还报失配
   说明差的是**实字符**。⛔ 比较符与数字**不在折叠范围内**：把 `≥3 个月` 写成 `>3 个月`、
   `18 周岁` 写成 `19 周岁` 都是真实篡改，照样拦，也**不该**靠改闸绕过。
2. **「OR 分支跨行拼接」**（`原文` 含 `；`/`/` 但未通过分段规则）→ 原方案里 `a) b) c)` 分支跨行排布，
   拼接成一条 `原文` 后不再是连续子串。闸9 允许**逐段命中**，但要同时满足：
   每段归一化后 **≥8 字**、各段在 raw 中的位置**顺序单调**、**≤6 段**。
   所以：补全被拼接时丢掉的字（别把分支缩写成 `过敏；心衰；高血压` 这种短段），保持分支顺序与原文
   一致。⛔ 乱序拼接（把 c) 的内容挂到 a) 的条件下）是语义篡改，本闸有意拦住它。
3. **「整轨重做」**（`raw最相近片段` 为空 → raw 里连相近片段都没有）→ 属凭空生成。
   先确认子代理读到的原文非空（`段行号` 是**试验方案.md**的坐标，⛔ 不可用于 read_file
   `eligibility_criteria_raw.md`，须用 `raw段行号`），再整轨重做。
   ⛔ **禁止**逐条改写 `原文` 去迁就已生成的结论。

`原文核对.OR分段通过` 列出被判为跨行拼接而放行的条目 —— 放行不等于无声，QC 会看这份清单。

⛔ **禁止为了让闸9 过而读脚本源码逆推归一化规则、再逐字符试**（thread `d393714d`：EX 轨解析因此
从 863k/23 步涨到 **2.81M/54 步**）。诊断块就是为了取代那个循环而存在的。

`extra_in_index` 有两种成因，处置不同：

| 成因 | 判断依据 | 处置 |
|------|---------|------|
| 索引残留 | 该 ID 的原文内容已被合并进另一条实体 | 删掉该索引键 |
| **实体丢失** | 该 ID 对应的原文条目在任何实体里都找不到 | **补回实体条目**（这是丢条，见下方守恒闸）|

## 逐条修订流程（执行者通用）

1. `read_file` **最新**的 `criteria_qc_{TRACK}.json`，只取 `blocking_issues`。
   `residual_issues`（建议级）**不在本轮强制修**——修它们会引入新的语义变更，
   反而给下一轮 QC 制造新发现，是不收敛的常见来源。
2. 取要改的条目：⛔ **用 `--show` 按条件ID 直取，禁止 `read_file` 读行区间**：
   ```bash
   python3 /mnt/skills/custom/criteria-parser/scripts/check_track_structure.py \
       --workspace /mnt/user-data/workspace --track {TRACK} --show EX-5-2,EX-13-1
   ```
   输出与文件逐字一致（含缩进），可直接据此确定该条目的 JSON Pointer，并附带该条在
   `描述索引` 里的值和所在行号。**单条 ≈300-800 字符，读行区间 ≈4,300 字符**，且不会读错位置
   ——`69612125` 里 `read_file` 量的 63% 就是"区间猜不准→再读一遍"造成的重复。
3. 逐条按 `type` 走下方处置手册，**一条 `blocking_issues` 对应一次 `apply_json_patches` 调用**（该条涉及的所有字段在同一批 patch 里改完；本阶段唯一允许的写入工具，见下方硬规则）。
4. 每改一条，同步改该条在 `描述索引` 里的键（条件ID 变了就必须同步，否则立刻造成
   `miss_in_index`/`extra_in_index`）。
5. ⛔ **全部 `blocking_issues` 修复完成后，一次性跑结构闸**（不要逐条跑）：
   ```bash
   python3 /mnt/skills/custom/criteria-parser/scripts/check_track_structure.py \
       --workspace /mnt/user-data/workspace --track {TRACK}
   ```
   闸输出按条件 ID 点名，失败时精准定位，不需要逐条查来隔离。
   若闸仍非零，只修点名条目，再跑一次——单次修订任务的结构闸控制在 1-2 次。
   脚本调用**不占** `task` 预算，这个成本可以忽略。
   > 对象级编辑已消除了字符串替换最常见的副作用——**漏逗号导致 JSON 不合法**
   > （历史故障 thread `345f2bf4`：连续两次报 `Expecting ',' delimiter`，第一次在 line 313、
   > 修完又在 line 401）：patch 作用于解析后的对象，序列化必然合法。批量闸仍会
   > 查条目数守恒、描述索引一致、QC 点名实体是否还在——这些与 JSON 合法性无关。
6. 全部改完 → 再跑一次结构闸，**必须带 `--qc`** + 下方守恒记账 → 都过了才触发下一轮 QC（`round += 1`）：
   ```bash
   python3 /mnt/skills/custom/criteria-parser/scripts/check_track_structure.py \
       --workspace /mnt/user-data/workspace --track {TRACK} \
       --qc /mnt/user-data/workspace/criteria_qc_{TRACK}.json
   ```
   ⛔ **`--qc` 不是可选项**：不带它，闸 7（QC 点名实体仍存在）、闸 8（原地打转探测）、
   闸 10（`upstream_issues` 已中性化）**一个都不会运行**，等于把三道防线全关掉。
   > thread `afb85bcd`：主代理侧 4 次结构闸调用**全都只写了 `--workspace --track`**，
   > 于是 `IN-10-4`/`IN-10-6` 的 upstream ↔ blocking 振荡在机制上完全隐形，
   > `criteria_qc_history_EX.json` 根本没生成（闸 8 只在带 `--qc` 时写历史）。
   > 另外 seq 651 那次还用了不存在的 `--criteria`/`--meta`，脚本只打印 usage —— 白烧一轮。
   > **参数只有 `--workspace` / `--track` / `--qc` / `--snapshot` / `--json` / `--show`，不要自创。**
7. ⛔ **改完不得再 `read_file` 产物"确认一遍"**：结构闸的 stdout 就是确认
   （`✅ 结构闸全过` / 点名的 problems），重读整份 JSON 只是把同样的结论再买一次。
   需要复核某条就用 `--show`，不要读全文。
8. ⛔ **修订完成判据（硬退出）**：结构闸带 `--qc` 全过 **且** 本轮 `blocking_issues` 每条都已
   处置（改 / 合并 / 补回 / 中性化）→ **立即返回，不再追加任何修改**。
   - `residual_issues`（建议级）不在本轮 scope（见第 1 步），不要顺手改。
   - `upstream_issues` 只做一次批量中性化（见下方专节），**不逐条循环校验**。
   - ⛔ 不得在 upstream / residual 上"改一条 → 跑一次闸 → 再改下一条"地循环。那正是 thread
     `3a745b38` 撞限的行为：14 条 upstream 逐条中性化 + 逐条校验，每条 ≈6-8 superstep，
     闸12 的建议级报警数随之单调上升，被读成"还有问题要改"，约 100 个 superstep 就这么没了。
     建议级 note 数量上升**不是**未完成的信号——判据只有上面这一条。

### ⛔ 改写方式（硬规则）

> **修订 `criteria_parsed_IN.json` / `criteria_parsed_EX.json` 只允许 `apply_json_patches`
> 的对象级形态（`{"pointer","op","value"}`）。**
> **`write_file` 与 `str_replace` 一律禁止**——全量、分片、`append=True` 都不行。

| 场景 | 允许的写入方式 | ⛔ 禁止 | 理由 |
|------|--------------|--------|------|
| **解析阶段**：新建本轨文件 | 分片 `write_file`（首批新建 + 后续 `append=True`，每批 ≤15 条）| 单次全量 `write_file` | 数万 token 单轮生成无中间进度信号，触发子代理看门狗（thread `31c168d2`）|
| **修订阶段**：改已有本轨文件 | **只允许 `apply_json_patches`（pointer + op）** | **`write_file`（任何形式）、`str_replace`** | LLM 重新生成文件内容 = 凭记忆重写，条目静默消失（thread `5d987e97`）；字符串定位则保证不了同一条目多字段的一致性 |
| 第一层客观修复 | 技能脚本 `json.load` → 改 → `json.dump` 覆盖写回 | LLM 自己写文件内容；脚本做语义修订 | 脚本是**机械变换**，不经过 LLM 重新生成文本，结构上不可能丢条 |

判据只有一条：**是否由 LLM 重新生成文件内容**。是 → 禁止；对象级 patch 只提交定点差异、
或脚本只做确定性变换 → 允许。

- ✅ **`apply_json_patches`，一条 `blocking_issues` 一次调用**（该条涉及的所有字段放同一批
  patch）。改动范围由 JSON Pointer 精确界定、可审计，未被 pointer 指到的条目不可能被动到；
  `replace` 不会凭空建字段，`expected_hash` 挡住陈旧读，任一 patch 不适用则整批不写。
  **`expected_hash` 用 `sha256sum <该轨文件> | cut -c1-12` 取**，自己刚写过之后要重新取一次。
  ⛔ `read_file` 不回报哈希、你也算不出 sha256，**不许凭印象填**（thread `93d8a2c6` 因此白掉
  一次调用 + 一次 `sha256sum` + 一次重试）。哈希不符时报错会给出当前哈希：本文件的 pointer 是
  `/四分类/{类目}/{条件ID}/...`，**key 寻址不受他处增删影响**，若要写的值不依赖刚读到的内容，
  可直接用它原样重试。
  ⚠️ 但要分清 `expected_hash` 管什么：它只回答"文件有没有被别人改过"，**不回答"我的 pointer
  还指不指向我要改的那一条"**。key 寻址下这两件事等价（不命中就报错），数字下标寻址下不等价
  ——thread `3a745b38` 的 27 次调用哈希全对、全返回 `OK`，却全写在了错误条目上。
- ⛔ **`write_file` 为什么连分片都不许**：单个方案单轨常有 20–30 条富字段条目（1.5–2 万字符），
  重新生成全文时模型是在「凭记忆重写」而非「定点修改」，条目静默消失、子条件被顺手合并、
  字段被简化都不会有任何报错。分片也救不了——`append=True` 只能往末尾追加，改不了已有内容；
  想靠「分片重建整个文件」等于把整份内容重新生成一遍，风险不减反增，还会先破坏 JSON 合法性。
  历史故障 thread `5d987e97`：一次 16165 字符的 `write_file` 让 `EX-7` 实体条目整条消失。
  解析阶段那条禁令（`31c168d2`）与本条**互相独立、方向相反**：解析阶段是**写不完**所以必须分片，
  修订阶段是**写丢了**所以只能定点改。⛔ **不要把解析阶段的分片节奏套用到修订上。**
- 确实需要重排大范围结构（例如一个原条从 6 个子条件合并成 1 个）时：用一个指向该条目的
  `replace`（`value` 给出合并后的完整对象），必要时配 `remove` 删掉被合并掉的子条目。
  **一个原条一次调用**，不要把多个原条的重排合成一次调用。
- ⛔ **`remove` 只允许作用于 QC 点名的条目**：用它删没点名的条目等于变相全量重写。
- 只需复核某条现值时用 `{"op": "get"}`，**不要为了看一条而重读整份文件**。
- ⛔ **严禁 bash 脚本做语义修订**（增删改子条件、改分类、改转化条件）。bash 只用于上方的
  结构自检与索引键的机械增删。
- ⛔ **严禁自创 schema 外字段**。`转化条件` 的合法字段只有
  `匹配字段` / `运算符` / `阈值` / `单位` / `或条件` / `除外` / `同义词` / `证据位置`
  （见 `references/schema_example.json`）。装不下的内容说明**颗粒度不对，应该拆条**，
  不是加字段。

### patch 组装的四条纪律（会话 f9231297 两条实症钉死）

- ⛔ **组装多 patch 批之前，先对该条目发一次 `{"op": "get"}`**（不写文件）确认现值与字段存在性。
  改动目标不熟的条目直接写 25 个 patch，第 13 个撞上「key X 不存在」时**前 12 个也不落地**
  （整批不写），一次调用白费 + 上下文重读。
- ⛔ **已存在的字段只准 `replace`，`add` 撞已有 key 直接报错**。见到
  `key 'add' already exists; add only creates` 不要原样重试，把该 patch 换成 `replace`。
- ✅ **单批 patch 越少越好**：按条目分小批（≤5 个/批），不要一条 25+ 个的大批包圆。
  一批 15 个里第 8 个错 = 7 个已算好的修改全部作废，重试还要重新读文件。
- ⛔ **数字下标 pointer 不可跨批次复用**：数组增删一项后旧下标静默指向别处
  （thread `3a745b38` 24 笔全写错条目）。改 `evidence`/数组字段用整数组 `replace`。
  > 故障（会话 `c80c47d9`，该会话**唯一未收敛**的阻断项）：`EX-12-1` 原文是
  > 「HBsAg **阳性** 且 HBV-DNA **> 10³ IU/ml**」，一组 `运算符`/`阈值` 表达不了
  > 「定性 + 定量」两种类型。修订子代理没拆条，而是新增了
  > `转化条件.并列条件='HBV-DNA > 10^3 IU/ml'`，QC 记为 residual：
  > 「『并列条件』字段未在 criteria-parser 的 转化条件 schema 中定义」，
  > 第 3 轮 `passed` 仍为 false。
  >
  > 正确改法：按 `parsing-rules.md` §拆分原则的**跨字段类型**判据拆成两条子条件
  > （`HBsAg 阳性` / `HBV-DNA > 10³ IU/ml`），同标 `逻辑关系=AND`，
  > `逻辑关系备注` 写明配对，各自持有类型一致的 `运算符`/`阈值`。
  > 该项现由 `check_track_structure.py` **闸 15** 阻断级拦下。

### 按 `type` 的处置手册

| QC `type` | 典型问题 | 处置 | 条数变化 |
|-----------|---------|------|---------|
| **拆分合理性**（过度拆分）| OR / 「任一」/「包括…」列举被误拆成多个 AND 子条件 | 合并回**单条**原条号（去掉子序号），分支写进 `转化条件.或条件`；说明性列举写进 `条件` 字段 | N → 1（**最危险，见守恒闸**）|
| **拆分合理性 / 拆分不充分**（拆分不足）| 含多个独立可判定事实的复合句压成一条；OR 分支内部的关键事实（次数/间隔/起始值）被泛化丢失；判定要件压在 `条件`（文本「A且B且C」）或 `或条件`（本应并行判定的分支）里 | **按 `parsing-rules.md` §拆分原则补拆**（必须拆分 AND / OR 异质替代分支 / `或组` 与 `或组语义` / 条件ID 编号规则），拆为连续子序号并行子条件；分支内部必要事实逐个写清，不得用「满足至少1项」这类泛化表述代替 | 1 → N |
| **拆分不充分**（QC 第二档子类型，`运算符=不限/阈值=null` + 文本承载判定） | 同上的文本承载形态——**这不是措辞问题，改写文字不构成修复**（会话 `881e7ba8`：两轮只改措辞、digest 全变而结构不动，3 轮不收敛） | 同上：按 `parsing-rules.md` §拆分原则拆条目；证据位置相同的并列要件才可留单条 | 1 → N |
| **分类正确性** | 同一原条同时含客观分支与研究者主观分支，被整条归入一个类目 | 按可获取性拆到两个类目，**原条号不变**，子序号在同一原条号下连续 | 1 → 2（跨类目）|
| **转化条件语义 / 与或逻辑错误** | 「且/或」混写；单指标满足即可 vs 全部满足被写混；豁免（「除外」）漏写 | **保持单条**，`或条件`/`除外` 改写成**互斥分支**的完整表达 | 不变 |
| **证据定位缺失** | `同义词`/`证据位置` 缺失或占位（`待人工判定`/`按原文匹配`/`原文关键词`） | 补齐为可检索的具体值（按 `parsing-rules.md` §转化示例 的形态） | 不变 |
| **覆盖完整性** | 原文条目遗漏；`描述索引` 有该 ID 而 `四分类` 无实体 | 按原文补回实体条目 | +N |
| **日期维度** | 同一条内多个分支各有不同时间窗被合并成一套规则；半衰期/替代洗脱期等不可执行表达 | 每个分支各自的 `参考事件` + `时间窗` 分别表达；无法结构化的依赖在 `条件` 里明示 | 不变 |
| **`upstream_issues`（第三档，不在 `blocking_issues` 里）** | 原文本身缺否定词/阈值/连接词，「忠实原文」与「可执行」互斥 | ⛔ **本轮立即中性化**（见下方专节），⛔ **不是"放着不动"** | 不变（或 −1 若删除）|

### `upstream_issues` 的中性化改法（本轮必做）

QC 报告里 `upstream_issues[]` 点名的条目**不在** `blocking_issues` 里，但**必须在本轮一起改**：
把它的确定性可执行表达降级，三选一（改完 `check_track_structure.py` 的闸 10 才会过）。

**① 降级为不可从病例获取**（最常用）：

```
apply_json_patches patches=[
  {"pointer": "/四分类/入选_可从病例获取/IN-10-4/可从病例获取", "op": "replace", "value": false}
]
```
同时把该条目从 `可从病例获取` 类目移到 `不可从病例获取` 类目，并在 `备注` 写明原因。

> ⛔ **pointer 一律按身份定位：`/四分类/{类目}/{条件ID}/...`。** `四分类` 的每个类目是**以
> `条件ID` 为键的对象（dict）**，没有下标这回事——key 命中即命中，不命中工具会报错，不需要
> 先用 `{"op": "get"}` 核对位置。
>
> ⛔ **`add` 只用于新建条目**（例如拆分出 `EX-11-4`）。条目已存在时改字段一律用 `replace`
> 指向该字段；对已存在的 key 用 `add` 会被工具拒绝（它会把整条替换、丢掉你没写的字段）。
> 跨类目移动 = 目标类目 `add` 新 key + 源类目 `remove` 旧 key，放在同一批 patch 里。
>
> 历史背景（thread `3a745b38`）：旧版类目是数组、pointer 只能用数字下标。一次 `add /21`
> 之后**跨调用**沿用旧下标，24 笔单字段写入全部落到前一条条目上（乙肝阈值写进 CNS 转移条目），
> 27 次调用**全部返回 `OK`、无一报错**，18 个 blocking 一个没修对还连锁污染 12 条，两轮 QC
> 白烧，最终撞 `recursion_limit=420`。数字下标只要在界内就一定"成功"，写对与写错在工具层同形，
> 所以既不报错也不留痕。dict key 把它变成"命中或报错"。

**② 保留类目、备注标注待核实**（原文歧义不影响可获取性时）：

```
apply_json_patches patches=[
  {"pointer": "/四分类/{类目}/{条件ID}/备注", "op": "replace",
   "value": "原文该分句疑缺否定词（待核实原件）；当前不编码为确定性约束"}
]
```
备注必须含 `待核实` / `原文歧义` / `缺否定词` / `原文缺词` / `不可判定` / `待人工确认` 之一
（闸 10 的识别词）。**同时**要把 `转化条件` 里的确定性阈值改成不可执行表达，
否则备注写了、条件仍在断言，等于自相矛盾。

> ⛔ **`运算符` 字段不得写 `待核实` / `原文歧义` 等状态词。** 它们不在标准运算符集合
> （`≥ ≤ > < = != in ∈ 不限`）内，闸12 会把每一条都报成"运算符不合规"——于是"改一条 +1 报警"，
> 形成正反馈。thread `3a745b38` 就是这么被误导的：seq 700→730 报警数 1→2→3→4→5 单调上升，
> agent 读成"还有问题要改"，逐条中性化 + 逐条校验烧掉约 100 个 superstep。
>
> **正确写法**：`运算符` 用 `不限`（在标准集合内）；状态词写进 `备注`（闸10 识别）；
> `转化条件.阈值` 改成不可执行表达（`null` 或文字描述）。即 **状态进备注，运算符保持合法**。

**③ 删除**（该条目确实是解析时凭歧义句臆造出来的）：对该条目用 `{"op": "remove"}`，
并在同一批 patch 里 `remove` 掉 `描述索引` 里对应的键。

⛔ **中性化 ≠ 放弃**：主代理仍要按 `criteria-qc-checklist.md` 第三档回 `uploads/` 原文核实该句
（允许破例、仅该句、必要时 `view_image` 看原页）；核实成功后**再恢复**可执行表达。
中性化只是让这一轮不再被它阻断，避免 upstream ↔ blocking 振荡（thread `afb85bcd`）。

**合并（过度拆分的处置）为什么最危险**：它是唯一会让条目**消失**的操作。删掉 `EX-9-1..-6`
之后必须确认合并后的 `EX-9` 真的写进去了。丢失时总条数看起来「符合预期地下降了」，
不做记账就抓不出来。

## 修订后守恒闸 —— 按 `blocking_issues` 记账

⛔ **每轮修订完成后必须记一次账**，把「预期条数」和「实测条数」写出来对比。
只看实测条数是否「下降得合理」是无效的。

```
修订前实测条数 N₀（上一轮结构自检的 total）
  − 合并操作减少的条数   Σ(该原条原有子条数 − 1)
  + 补拆操作增加的条数   Σ(拆后子条数 − 1)
  + 按可获取性跨类目拆分增加的条数
  + 覆盖完整性补回的条数
  = 预期条数 N₁
```

实测 `N₁` ≠ 预期 → **一定有条目在改写中丢失或串位**，禁止触发下一轮 QC，先定位补回。

记账示例（thread `5d987e97` 的 EX 轨 R1 修订，若当时记了这笔账即可当场发现丢条）：

```

合并 EX-2（2→1）  −1
合并 EX-4（3→1）  −2
合并 EX-7（3→1）  −2
合并 EX-9（6→1）  −5
EX-13 按可获取性拆（1→2） +1
预期 N₁ = 20 ；且 EX-2 / EX-4 / EX-7 / EX-9 四个实体必须各自存在
实测发现 EX-7 实体不存在 → 立即补回，而不是等下一轮 QC 报「覆盖完整性」
```

**除条数外必查（脚本代劳，不用手数）**：修订后带上本轮 QC 报告再跑一次，
脚本会按 `blocking_issues[].condition_id` 的原条号**逐个点名**核对实体是否还在（闸 7），
并用 `末条号` 做无基线的原条号全覆盖检查（闸 6）：

[EX] ⛔ 闸6 原条号无任何实体条目：['EX-7']（末条号=17）→ …必须补回

## 轮次配额纪律

每轨最多 **3 轮** QC（原则 7）= 首检 1 轮 + 修订后复检 2 轮，即**2 次修订机会**。
**一次错误的修订方式会吃掉其中一次**，而且吃掉的方式最隐蔽——不是"没修好"，
而是"修出了新问题"，下一轮 QC 报的是**修订自己制造的错**，配额却照样扣。

thread `5d987e97` 的实际代价（当时上限还是 2 轮）——R1 修订用全量 `write_file` 丢了 `EX-7`，
R2 QC 因此报出「EX-7 实体遗漏」这个**由修订本身制造的新问题**而不通过，直接触顶上限、
全局暂停请示用户。用户放行后改用 `str_replace` 逐条修，R3 两轨立即 `passed=true`。

这正是上限从 2 提到 3 的依据：那次若有第 3 轮配额，R3 本可在**无人介入**下收敛。
但配额变宽**不是**降低修订质量要求的理由——`5d987e97` 真正的问题是修订方式错，
不是配额不够；配额只是给"修订本身出错"留一次兜底。

推论：**修订的正确性比修订的速度重要得多**。宁可多花几次定点编辑调用，
也不要用一次全量重写去省调用次数。
