# criteria QC 检查清单（按轨执行）

> 每轨一份 QC：`criteria_qc_IN.json` / `criteria_qc_EX.json`。
> 两层协同收敛，**每轨最多 3 轮**（首检 1 轮 + 修订后复检 2 轮 = **2 次修订机会**；
> 编排层负责轮次计数与达上限后的处置）。
>
> ⛔ **「轮次」只计语义 QC**：`task(quality-control)` 返回一次 = 一轮。
> 第一层结构闸的校验与修复、乃至闸 9 命中触发的**整轨重做解析**，**都不计入轮次预算**，
> 可反复跑到 `exit 0`。理由：结构问题是客观的、有机械判据、修复不消耗语义判断力；
> 把它计入轮次等于用语义预算买结构收敛（thread `afb85bcd`：首检就命中
> `[IN] 闸9 2/27`、`[EX] 闸4 混用 + 闸9 6/26`，靠整轨重做才过——若这算轮次，
> 3 轮语义预算在语义 QC 开始前就已被侵蚀）。
>
> ⛔ **轮次按轨独立计数**：IN 与 EX 各有自己的 3 轮，**互不影响**；一轨触顶不冻结另一轨
> （thread `afb85bcd`：IN 触顶时 EX 才第 2 轮、还有 1 轮预算，被一起停下，
> 而 EX 当时只剩 2 项阻断，很可能第 3 轮就过了）。
>
> ⛔ **QC 结论只能由 `task(quality-control)` 子代理写**。主代理只读不写——
> 禁止用 `write_file`/`str_replace` 把 `blocking_issues` 挪进 `residual_issues`、
> 清空 `blocking_issues`、或把 `passed` 改成 `true`。修订完必须由 QC 子代理复核后才算通过。
> 历史故障 thread `5a1c8d95`：主代理把 3 条阻断项标注「已达QC轮次上限，带建议放行」后自行置
> `passed=true`，未经复核即推进判定；`parse_pack.py` 的 QC 闸现在会检出这种自我放行痕迹并阻断。

## 第一层 — 结构/格式快速收敛（允许并鼓励 bash 脚本）

**允许**用 `bash` 脚本（Python/jq）对本轨 `criteria_parsed_{TRACK}.json` 做**客观格式/结构**
校验与**就地快速修复**，目标是进入语义 QC 前把格式问题一次性收敛清零，避免语义 QC 被结构噪声
干扰。可修复项限于**确定性、客观**的问题：

- JSON 合法性、必填字段存在性（缺失补 `null`）
- 条件ID 编号连续性/唯一性（重排子序号）
- 四分类枚举合法性（本轨只允许本轨 2 个类目）
- 条件ID 前缀与轨一致（IN 轨全 `IN-*`、EX 轨全 `EX-*`）
- 描述索引与本轨四分类条目**双向**一一对应（`miss_in_index` / `extra_in_index` 均为空）

脚本修复后覆盖写回本轨文件并打印修复项清单。这里的覆盖写回是**脚本**
`json.load` → 改 → `json.dump` 的机械变换，结构上不可能丢条，与「LLM 用 `write_file`
重新生成文件内容」是两回事——后者在修订阶段一律禁止（见 `criteria-repair.md`）。

⛔ **本层是第二层的硬前置**：上述客观项未清零**禁止**发 `task(quality-control)`，
且本层检查**不得与 QC 子任务同轮发出**。检查一律用技能脚本、**禁止现写内联 python**：

```bash
python3 /mnt/skills/custom/criteria-parser/scripts/check_track_structure.py \
    --workspace /mnt/user-data/workspace
```

`exit 2` 即阻断（**10 个闸**的判据见脚本 docstring；修订后的用法见 `criteria-repair.md`）。
脚本每次运行会落盘 `criteria_structure_gate_{TRACK}.json`（含 `exit_code` + 被检文件内容哈希），
**QC 委派模板要求子代理开工前先读它**：`exit_code != 0` 或文件缺失 → 子代理自行拒工。
这是对「结构闸未过不得派 QC」的硬化——不依赖主代理守规矩。
历史故障 thread `5d987e97`：结构自检与 2 个 QC 子任务同轮发出，
17 项描述索引/四分类不一致未收敛就进了语义 QC，QC 把结构噪声当语义问题报出，浪费轮次配额。

⛔ **对齐方向唯一**：以 `四分类` 实体为准修 `描述索引`；**禁止**为了让索引对上而删改实体条目
或退回拆分粒度——拆分粒度只能由语义 QC 的 `blocking_issues` 驱动改变。

> `汇总统计` 不在本轨维护——它是全篇级字段，由 `parse_pack.py assemble` 重算。

## 取证方式（⛔ 先读取证包，不要逐条 grep）

**取证的默认入口**：`/mnt/user-data/workspace/criteria_qc_bundle_{TRACK}.md`
（由主代理在派 QC 前用 `scripts/criteria_qc_bundle.py` 装配）。它按**原条号**分组给出：
raw 原文段 + 该组各子条件的 `转化条件`/`日期维度`/`或组` 要素 + 机械预判
（`原文` 逐字可查性、`阈值` 是否需定档、闸12 是否命中外部标准）。

- ⛔ **禁止逐条 `grep` raw 原文取证**，⛔ **禁止写内联 `python3 -c` 去 print 字段** ——
  会话 `e3c15416` 的 `EX track QC round 2` 就是这么用掉 **77 步**（`bash 28 / read_file 11`）
  并撞上 `max_turns=150` **失败**的；每一步都要重传此前全部历史（实测 18×~30×）。
- 取证包不够用时，只对**个别**条目按它给出的行号定点 `read_file` 补读，不要整篇重读。
- 只需看某个字段现值时用 `apply_json_patches` 的 `{"op": "get"}`，它**不写文件**。

> **本节曾经形同虚设（会话 `c2518bc7`，2026-08-10）**：主代理按硬前置把两轨取证包**装配好了**
> （IN 9,471 字符 / EX 19,538 字符），但下方「QC 委派模板」的输入清单里**没有这个文件**，
> 而模板又写着「只读这两个文件…禁止 ls/glob 探索」——白名单直接把「取证默认入口」排除在外。
> 结果 6 个 QC 子代理**一次都没读过取证包**，全部退化成：整篇读 `criteria_parsed_{TRACK}.json`
> → 被 50k 字符上限截断 → 按行窗分页补读 8~13 次（还夹着一次 `bash wc -l` 只为问文件多长）
> → 第三轮再补 **20 次内联 `python3 -c`** 逐条 print 字段。单轨第三轮 `bash + read_file`
> 因此从 17 反弹到 **35**。教训：**规则写在技能里、白名单写在模板里，两者矛盾时模板赢** ——
> 所以取证入口必须出现在模板的输入清单里，且带自检（缺文件即拒工），不能只靠本节的文字禁令。

## 第二层 — 语义 QC（`task(quality-control)`，核心，脚本不可替代）

语义级质控**必须**委派 `task(quality-control)` 子代理，由 LLM 推理完成。
**核心检查：逐项判断每条条件的语义逻辑是否合理**：

1. **拆分合理性** —— AND 应拆未拆 / **OR 异质替代分支应拆未拆** / 豁免被误拆为独立条件 /
   注释误拆 / 语义等价重复拆分（同一事实的单位换算·参考范围变体·同类列举被拆成多条）；
   ⚠️ 判据是"各分支是否需要查不同的证据位置/匹配字段"：需要 → 应拆成并行子条件并标
   `或组`/`或组语义`；不需要 → 应留在 `或条件` 字段内。
   典型应拆案例：`对试验药物的任一活性成分或辅料过敏者，或有特异性变态反应病史（哮喘、风湿、
   湿疹性皮炎）仍需全身性药物治疗者或曾发生过其它严重的过敏反应者` → 4 条（活性成分过敏 /
   辅料过敏 / 病史且仍需全身治疗 / 其它严重过敏反应），四支证据位置各不相同。
1b. **`或组` 语义正确性（阻断级）** —— 拆出的并行分支必须标同一 `或组`，且 `或组语义` 与轨匹配
   （入选=`任一满足即整条满足`，排除=`任一触发即整条触发`）。入选轨漏标或标反会让判定侧按
   约束 18「全部入选符合」汇总，把"满足其一即可"变成"必须全部满足"，**错误淘汰患者**。
   该项已由 `check_track_structure.py` 闸 11 机械校验，语义 QC 只需复核"分支划分是否合理"；
2. **分类正确性** —— 「可/不可从病例获取」判定是否准确；同一条含客观分支 + 研究者主观分支时
   是否按可获取性拆到两个类目（不得整条归一类而丢掉可客观核验的分支）；
3. **转化条件语义** —— 运算符/阈值/单位是否忠实原文，`或条件`/`除外` 逻辑表达是否正确，
   且"可从病例获取"条件的 `同义词`/`证据位置` 非空。**阈值/运算符的可执行性按下方三档定档**。
4. **日期维度** —— 时间窗/参考事件/区间逻辑是否正确；
5. **覆盖完整性** —— 是否有原文条目遗漏或被合并丢失；`描述索引` 里出现的条件ID 必须在
   四分类中有对应实体条目（历史阻断项 CQC-R2-001：描述索引有 IN-3-3 而四分类中不存在）。

### 阈值/运算符可执行性：三档判据（**首轮**定档，不得拖轮次）

⚠️ 这条判据是本清单与 `SKILL.md` 之间**唯一**曾经互相矛盾的地方，必须按此执行：
`SKILL.md` 的 `转化条件` 字段定义允许 `"阈值": 数值 或 "文字描述" 或 [离散值]` —— "文字描述"
**合法**，但只在第三档的意义上合法。别再把所有文字描述阈值一律判阻断。

| 档 | 判据 | 分级 | 动作 |
|---|---|---|---|
| ① 可执行 | 数值 / 离散值集合 / 区间，且 `运算符` ∈ `≥ ≤ > < = != in ∈ 不限` | 通过 | 无 |
| ② 可结构化却没结构化 | 原文**自带**判定要件，只是被写成一句自然语言；改写即可执行 | **阻断级** | 按下表子类型报 `type`，`action` 写具体操作 |
| ③ 依赖外部评价标准 / 本质是相对比较 | 判定要件写在 **PCWG3 / RECIST V1.1 / iRECIST / CTCAE / NYHA / Child-Pugh** 等外部标准里、方案原文没给；或本质是相对比较（「与上次骨扫描相比」）、无绝对阈值 | **`upstream_issues`** | **首轮**归档，不计入 `blocking_issues`、不占阻断额度、不阻断 `passed` |

⛔ **第二档禁止报笼统 `type: 转化条件不可执行`** —— 那是一类不指路的结论，修订方只能猜
（会话 `881e7ba8`：IN 轨两轮 11 条全报它，修订每轮只改措辞、`运算符=不限/阈值=null`
纹丝不动，3 轮不收敛）。必须按下表报**子类型**，`action` 写可执行操作：

| 子类型 `type` | 识别特征 | `action` 必须写 |
|---|---|---|
| **拆分不充分** | 多要件压在文本里：`条件` 字段承载「A且B且C」/ `或条件` 承载本应并行判定的分支 / `子条件`=原文整条含多个独立可判定事实 | **「拆分为 {轨}-{条}-{N}.. 并标 `或组` {X}-OR」**，拆分按 `parsing-rules.md` §拆分原则（必须拆分 AND / OR 异质替代分支 / `或组` / 条件ID 编号规则）执行 |
| **与或逻辑错误** | 「且/或」混写、单指标满足即可 vs 全部满足写混、豁免（「除外」）漏写 | 「保持单条，`或条件`/`除外` 改写为互斥分支完整表达」 |
| **证据定位缺失** | `同义词`/`证据位置` 缺失或占位（`待人工判定`/`按原文匹配`/`原文关键词` 这类不可检索占位串） | 「补齐 `匹配字段`/`同义词`/`证据位置` 为可检索的具体值」 |
| **字段不可执行** | `运算符`/`阈值` 缺失或非法（非第三档外部标准情形） | 「按原文落 `运算符`+数值/离散值 `阈值`」 |

第二档的样板（历史阻断项 `CQC-R2-003`）：`无肝转移且ALT≤3×ULN且/或AST≤3×ULN` —— 要件齐全，
只是没收敛成结构化字段；三个要件证据位置各不相同 → 报 `拆分不充分`，action = 拆并行子条件。

第三档的样板（会话 `1fee1395`）：`IN-5-1`（PSA 进展，原文是 PCWG3 的缩写版、缺 ≥25% 增幅与
≥3 周确认）、`IN-5-2`（软组织进展"根据 PCWG3 和 RECIST V1.1 定义"）、`IN-5-3`（骨病灶进展 =
"与上次骨扫描相比至少两个新发病灶"，相对比较）、`IN-7-1`（RECIST V1.1 可测量病灶依赖
最长径≥10mm 等标准内定义）、`IN-7-2`（PCWG3 骨转移病灶判定依赖示踪剂摄取 + 其他影像确认）。
这 5 条在该会话被判了两轮阻断、到 R3 才中性化，**两轮配额纯空转**——它们从第一轮起就是第三档。

⛔ **别把第三档当"放弃"**：仍要写 `原文引用` + `缺什么` + `建议核实位置`，主代理照第三档流程
回原件核实或 `ask_clarification`。只是它不再消耗阻断额度。

**机械辅助**：`check_track_structure.py` **闸 12** 会把「`运算符` 不在标准集合内」的条目一次性
点名，并回报命中的引用型标准名（命中即第三档可能性最高）。它是**建议级**——定档仍由你做，
但两轨必须用同一口径。实测该会话 IN 轨的非标准运算符恰好是 `进展`×3 + `存在`×2，
与那 5 条 upstream **完全重合**。

## ⛔ 禁止用 bash 脚本做语义修订（历史违规根因）

bash 脚本仅用于第一层**客观格式**收敛；**严禁 bash 脚本做语义修订**
（如 `find_item`/`pop_item` 批量增删改子条件）。语义修订必须由主代理 LLM 逐条判断后用
`write_file`/`str_replace` 完成。

原因：脚本批量改语义会破坏编号连续性、遗漏关联条目、引入新结构问题，
反而给下一轮 QC 制造新"发现"，导致不收敛。

## ⚠️ 第三档：`upstream_issues`（问题在上游原文，结构化层无解）

有一类问题**无论怎么改结构化条目都过不了 QC**：原文本身有缺陷（PDF→MD 提取丢字/丢否定词、
句子自相矛盾），此时「忠实原文」与「可执行」互相排斥——写成确定条件叫超出原文补写，
写成「待核实」叫不可执行。这不是修订方的错，继续标阻断只会让 QC 原地打转、耗尽轮次配额。

**判据（满足其一即归此档，不再计入 `blocking_issues`）**：

- 同一 `condition_id` 连续两轮被判阻断，且两轮 `action` 要求**互相矛盾**（一轮要 A、下一轮否定 A）；
- 本轮 finding 自身承认两条路都不合规（形如「若按 X 则…；若按 Y 则…；无论哪种情况都…」）；
- 原文该句缺少必要成分（否定词、阈值、单位、连接词）导致语义不可判定；
- **阈值的判定要件写在外部评价标准里**（PCWG3 / RECIST V1.1 / iRECIST / CTCAE / NYHA /
  Child-Pugh…）、方案原文没给，或本质是相对比较（「与上次相比」）而无绝对阈值 ——
  见上方「阈值/运算符可执行性：三档判据」第三档。⚠️ 这一条**首轮即可判定**，
  不需要等"连续两轮阻断"来触发；等两轮就是白烧配额（会话 `1fee1395` 的 IN-5-*/IN-7-* 共 5 条）。

**QC 子代理的动作**：写进 `upstream_issues[]`（schema 见下），**不计入** `blocking_issues`
（因此不阻断 `passed`），并在条目里给出 `原文引用` + `缺什么` + `建议核实位置`。

**主代理的动作（四步；第 0 步与第 1 步并行，不是二选一）**：

0. ⛔ **本轮立即中性化**（不等核实结果，交给本轮的修订子代理一起做）——把该条目的
   **确定性可执行表达降级**，三选一：
   ① `可从病例获取` 改 `false`，并在备注说明原因；
   ② 保留在原类目但在**备注写明原文缺什么**（须含 `待核实` / `原文歧义` / `缺否定词` 等标记词）；
   ③ 该条目确实多余则删除，并同步 `描述索引`。

   **为什么「放着不动」是错的**：不动保留的恰是解析时写下的确定性表达（如把
   「在 1 周内没有输注过血小板，接受过…治疗」编码成「两项均无」），它**超出原文**；
   下一轮 QC 会正确地把它判为「上游歧义未隔离/第二档子类型」并**升级为 `blocking_issues`**，
   于是同一批条目在 upstream ↔ blocking 之间振荡，白烧轮次配额。
   > 历史故障 thread `afb85bcd`：R1 已把 `IN-10-4`/`IN-10-6` 正确归入 `upstream_issues`，
   > 但主代理给修订子代理的指令是「先不要硬改成确定结论；保持忠实原文，不要伪造修复」，
   > 子代理**正确地**完全不动（result 明确回报「未做伪造性『确定修复』」）；
   > R2 的 QC 于是把这两项升级为 blocking，占掉四项阻断里的两项；R3 中性化后才回落 upstream。
   > 一整轮配额是纯浪费 —— 缺的不是纪律，是「核实前该怎么处置已写入的表达」这一步。

   ⚠️ 给修订方的指令必须写**要做什么**（中性化），不要只写**不许做什么**（别伪造修复）——
   后者会被合理地理解成「别动」。
   **`check_track_structure.py` 闸 10 会机械检查这一步**：`upstream_issues` 点名的条目若仍是
   「条目存在 + `可从病例获取` 不为 false + 通篇无待核实标记」→ `exit 2`。
   （闸 10 需要 `--qc`，见下方「复检必须带 `--qc`」。）

## 阻断/建议分级（通过门槛量化）

- 第一层**客观项**（结构/编号/枚举/前缀一致）**必须全过**，由 bash 脚本收敛保证。
- 第二层语义项分「**阻断级**」「**建议级**」与「**上游级**」（`upstream_issues`，见上一节）：
  - **阻断级**（计为不通过）：分类错误、关键 OR/豁免逻辑错误、`或组`/`或组语义` 缺失或与轨不符、异质 OR 分支应拆未拆、条目遗漏、
    `同义词`/`证据位置` 缺失、第二档四子类型（拆分不充分 / 与或逻辑错误 / 证据定位缺失 / 字段不可执行）、描述索引与实体不一致。
  - **建议级**（仅记录，不作为不通过理由）：拆分粒度倾向、乐观/保守偏好等主观判断。

### ⛔ 全量报告，不是增量报告（收敛纪律）

> **规则变更（2026-08-17，会话 `c80c47d9`）**：旧规则是「对比上一轮报告去重，仅报告『未修正』
> 或『新发现』问题」，**已废除**。
>
> 「只报未修正或新发现」在语义上等价于「允许本轮才第一次看某些条目」。它本意是省 token，
> 实际效果是把**全量复查降级成差分复查** —— 第 1 轮没看仔细的条目，第 2 轮才"新发现"。
> 该会话 EX 轨 `criteria_qc_history_EX.json` 两轮 `blocking_ids` **零交集**
> （R1: `EX-1-1/EX-14/EX-15-1/EX-6/EX-9-3`；R2: `EX-12-1/EX-12-2/EX-12-4`），
> 第 3 轮 `passed` 仍为 false，返工 1.72M token / 535s ≈ 首次解析的全部开销。

**每一轮**都必须逐条复核**全部**条目，报告里列出**全部**已知问题，用 `status` 区分状态：

| `status` | 语义 | 是否阻断 |
|---|---|---|
| `open` | 尚未修复（**缺 `status` 字段一律按 open 处理**） | 是 |
| `fixed` | 上一轮提出、本轮复核确认已改好 | 否（留在报告里供追溯） |
| `upstream` | 经复核确认属第三档（原文缺陷），应移入 `upstream_issues` | 否 |

**上一轮报告只用于标注状态，不用于缩小本轮范围。**

- 第 1 轮就要把所有档次一次找完：阻断级、建议级、上游级。
- 第 2 轮起**只允许**两种动作：① 把 `open` 改 `fixed`；② 纠正误判的档次。
- 第 2 轮起出现 `first_seen_round > 1` 的阻断项属**异常**，必须标 `late_discovery: true`
  并在 `finding` 里说明第 1 轮为何漏检 —— 这是编排层的收敛指标，验收口径要求它为 0。
- `coverage.reviewed` 必须等于 `coverage.total_entities`。后者由主代理从
  `criteria_structure_gate_{TRACK}.json` 的 **`total`** 字段（结构闸已落盘，无需新增）读出后
  填入委派模板的 `{total}`，**不由 QC 子代理自己数** —— 自己数就没有外部基准了。
  两者不相等时 `parse_pack.py` 的 QC 闸判未收敛并要求重跑。

## `criteria_qc_{TRACK}.json` schema

`passed = blocking_issues 里没有 status=open 的条目`（`upstream_issues` **不**计入，见上一节——
它不是修订方能解决的问题，计入只会让 QC 原地打转；`status=fixed` 的条目留在 `blocking_issues`
里供追溯，也不计入）。字段名与 `parse_pack.py` 的 QC 闸读取的字段一致：

```json
{
  "track": "IN",
  "passed": false,
  "round": 2,
  "coverage": {"total_entities": 28, "reviewed": 28},
  "blocking_issues": [
    {"id": "CQC-R1-001", "condition_id": "IN-8", "type": "分类错误",
     "finding": "……（可选，问题描述）", "action": "改判为可从病例获取",
     "status": "fixed", "first_seen_round": 1},
    {"id": "CQC-R1-002", "condition_id": "IN-10-4", "type": "拆分不充分",
     "action": "拆分为 IN-10-4-1..N 并标或组 IN-10-4-OR（依据 parsing-rules.md §拆分原则）",
     "status": "open", "first_seen_round": 1},
    {"id": "CQC-R2-001", "condition_id": "IN-12", "type": "……",
     "action": "……", "status": "open", "first_seen_round": 2, "late_discovery": true}
  ],
  "residual_issues": [
    {"id": "CQC-R1-009", "condition_id": "IN-5", "type": "拆分粒度", "action": "建议细化分支"}
  ],
  "upstream_issues": [
    {"id": "CQC-R3-U01", "condition_id": "IN-10-4", "type": "原文缺词",
     "原文引用": "血小板 ≥ 100×10^9/L，在 1 周内没有输注过血小板，接受过促血小板生成素…治疗。",
     "缺什么": "第二个分句缺否定词，字面与前句矛盾；忠实原文与可执行互斥",
     "建议核实位置": "uploads/试验方案.pdf 入选标准第10条 血液学一行"}
  ]
}
```

`parse_pack.py` 的 QC 闸判定为「未收敛」的四种情形：

1. `passed != true`；
2. `blocking_issues` 里存在 `status` 不是 `fixed`/`upstream` 的条目（即使 `passed` 被写成 `true`）
   —— ⚠️ **缺 `status` 字段按 `open` 处理**，所以旧格式报告（无 status）的行为与改版前一致；
3. `coverage.reviewed < coverage.total_entities`（本轮没看全 → 结论不可信）。`coverage` 整体
   缺失时不判问题，旧 workspace 不受影响；
4. 检出自我放行痕迹——顶层 `note`/`status`/`conclusion` 或任一 `residual_issues[].status`
   含「带建议放行」/「轮次上限」，或存在 `round_limit_released: true`。

第 3 条的存在意义：达轮次上限仍有阻断项时，正确动作是**暂停并请示用户**，
而不是把阻断项降级成建议后自行放行；因此「带建议放行」标记在 criteria QC 上属非法状态。

## 修订纪律（主代理执行）

修订的完整处置手册见 **`criteria-repair.md`**（唯一权威：按 QC `type` 的改法、前置结构闸、
条数守恒记账闸、三轨并行、故障档案）。此处只列与 QC 交接相关的约定：

- **修订一律委派修订子代理**（能改文件：`general-purpose`/`data-extractor`，⛔ 不得用
  `quality-control`），主代理 ⛔ 禁止亲做逐条修订;委派 prompt 由
  `render_parse_prompt.py --kind repair` 机械渲染（见 `phase2-orchestration.md`「委派铁律」）。
  修订子代理只允许 `apply_json_patches` 对象级修改（硬规则见修订委派模板;
  `write_file`/`str_replace`/bash 重写一律禁止——LLM 重新生成文件内容会静默丢条目,
  thread `5d987e97`：`EX-7` 实体在一次 16165 字符的 `write_file` 中消失）。
- 修订针对**最新** `criteria_qc_{TRACK}.json` 的 `blocking_issues`（阻断级）+ `upstream_issues`
  中性化;建议级不在本轮强制修。
- 修订完成 → 结构自检 + 条数守恒记账（见 `criteria-repair.md`）都过了才触发下一轮
  QC（`round += 1`），由 QC 子代理重新写结论。
- 两轨的修订互不阻塞，且与 OCR 并行：IN 轨修订时 EX 轨可继续 QC/修订、OCR 子任务照常在途。
