# 解析规则（唯一权威）

> **谁读这份文件**：解析子代理（`task` prompt 由 `parse-delegation.md` 模板生成，模板会给出本文件
> 的绝对路径）与修订子代理。主代理**不需要**常驻这些规则——它不亲自解析、也不亲自修订。
>
> **为什么单独成篇**：子代理的 `skills` 白名单是 `[]`，它不会自动加载任何 SKILL.md，只能按模板
> 指路 `read_file`。规则原先长在 `SKILL.md` 里，而模板又写着「规则：…/SKILL.md（四分类体系 /
> 拆分原则 / …）」，于是解析子代理为了拿规则去**整篇读**一个 38KB 的编排手册
> （thread `93d8a2c6` 实测：本技能 SKILL.md 被整篇读 4 次 + 分段读 3 次，是全会话最高）。
>
> ⛔ **本文件的小节名是外部契约**：`parse-delegation.md` 与 `criteria-qc-checklist.md` 按
> 「四分类体系 / 拆分原则 / 条件ID编号规则 / 条件转化规则 / 日期维度规则 / 可获取性判定标准」
> 这些名字指路。**改写内容可以，改动小节名不行**（会让模板里的引用变成悬空）。
>
> 故障叙述一律不在这里，在 `failure-archive.md`。本文件只放**live 规则**。

## 四分类体系

| 分类 | 含义 | 判定依据 |
|------|------|----------|
| **入选_可从病例获取** | 入选条件，可从客观病历数据验证 | 客观诊断、分期、检验值、影像、用药史、手术史 |
| **排除_可从病例获取** | 排除条件，可从客观病历数据验证 | 同上 |
| **入选_不可从病例获取** | 入选条件，需研究者/受试者主观参与 | 知情同意、受试者承诺、预后预估、未来计划、研究者主观评估 |
| **排除_不可从病例获取** | 排除条件，需研究者/受试者主观参与 | 同上 |

## 拆分原则（最小子颗粒度）

### 必须拆分（AND 关系）
- 使用"且"、"并"、句号分隔的并列条件 → 每个独立子条件
- 数值范围的上下限 → 各自独立（如"18-70岁" → "≥18" + "≤70"）
- 主条件 + 附加时间窗要求 → 拆为数值条件 + 洗脱期条件

#### 两种**不得**归入「限定性 AND」的 AND（必拆）

下方「仍然不拆」允许**限定性 AND**（修饰同一事实）留在一条内。以下两类长得像限定性 AND
但必拆 —— 判据不是"是否在描述同一件事"，而是**一条子条件的字段能不能装下它**。

**(a) 跨 `可从病例获取` 边界**：一半是客观病历数据、一半需研究者/受试者主观参与。不拆则整条
只能标一个 `可从病例获取` —— 标 `true` 会让判定侧去病历找主观评估（必然「无法判断」），
标 `false` 会丢掉可客观核验的那一半。

> `EX-1`（`MSI-H 或 dMMR，且经研究者评估适合免疫治疗`）→ `EX-1-1`（MSI-H/dMMR，可获取
> =`true`）+ `EX-1-2`（研究者评估，`false`）；同标 `逻辑关系=AND`、`逻辑关系备注` 写明配对。
> **闸 16**（建议级）提示未拆形态。

**(b) 跨字段类型（定性 × 定量）**：一半是定性判定（阳性/阴性、有/无、存在/不存在）、一半是
定量阈值（`>`/`≥`/`<`/`≤` + 数值 + 单位）。`转化条件` 只有**一组** `运算符`/`阈值`，装不下两种。
⛔ 也**禁止自创 schema 外字段**去装（合法字段见 §条件转化规则）——装不下说明**颗粒度不对、
应该拆条**。故障见 `failure-archive.md`#定性阈值与定量要件混用。

> `EX-12-1`（`HBsAg 阳性 且 HBV-DNA > 10³ IU/ml`）→ `HBsAg 阳性`（`=`/`阳性`）
> + `HBV-DNA > 10³ IU/ml`（`>`/`1000`/单位 `IU/ml`）。

**闸 15**（阻断级）：`阈值` 是定性词 且本条 `子条件` 含 `[><≥≤]` + 数值 → 阻断。
⚠️ 闸只看 `子条件` 不看 `原文`：同一原条号的子条件**共享**整段 `原文`，按 `原文` 判会连坐误报
同组兄弟。故 `子条件` 必须写本条**专属**的那一支，不要抄整段。

**与限定性 AND 的边界**：限定性 AND 的判据是**单看一半无法判定是哪种情况**（「有某病史 **且**
仍需全身治疗」——单看"仍需治疗"不知是哪种病）。若两半各自都能独立判定、只是共同构成一个
诊断名（`HBsAg 阳性` + `HBV-DNA 超阈值` 共同定义"活动性乙肝"），按 (a)/(b) 拆。

### 必须拆分（OR 关系的异质替代分支）

> **规则变更（2026-08-06）**：旧规则是「OR 关系整体保留、不拆分」，已废除。
> 整体保留会让判定子代理在一次比对里回答多件互不相干的事，实测倾向只答最容易的那一支；
> 且各分支的证据位置往往不同，共用一套 `同义词`/`匹配字段` 本身就不成立。

**"或"、"和/或"、"任一"、"以下之一"连接的替代分支，若彼此是异质事实 → 拆成并行原子子条件**，
并用 `或组` 标记同组、`或组语义` 声明汇总方向。

**拆不拆的唯一判据：各分支是否需要查不同的证据位置 / 匹配字段？**
需要 → 异质，拆；不需要（是同一事实的不同写法）→ 不拆。

**示例（排除标准第1条）**：

> "对试验药物的任一活性成分或辅料过敏者，或有特异性变态反应病史（哮喘、风湿、湿疹性皮炎）
> 仍需全身性药物治疗者或曾发生过其它严重的过敏反应者；"

拆成 4 条并行子条件，同组 `EX-1-OR`：

| 条件ID | 子条件 | 匹配字段（证据位置不同 → 应拆） |
|---|---|---|
| `EX-1-1` | 对试验药物的任一活性成分过敏 | 用药史 / 过敏史（试验药成分） |
| `EX-1-2` | 对试验药物的任一辅料过敏 | 过敏史（辅料） |
| `EX-1-3` | 有特异性变态反应病史（哮喘、风湿、湿疹性皮炎）**且**仍需全身性药物治疗 | 既往史 + 用药史 |
| `EX-1-4` | 曾发生过其它严重的过敏反应 | 过敏史（严重过敏/anaphylaxis） |

注意该例的两个细节：
- `EX-1-3` 括号里的"哮喘、风湿、湿疹性皮炎"是**同类举例**，不再往下拆；
- `EX-1-3` 内部的"病史 **且** 仍需全身性药物治疗"是**限定性 AND**（单看"仍需全身治疗"无法判定
  是哪种病），保留在一条内，不按 AND 规则拆开。

### 仍然不拆（同一事实 / 豁免）

- **同一事实的等价表述**：单位换算（`睾酮<50 ng/dL 或 <1.7 nmol/L`）、参考范围变体
  （`尿蛋白≤1+ 或 24h定量<1.0g`）、同义指标 → 写进 `或条件` 字段，不拆。
- **同类列举**：`锶-89、钐-153、铼-186、铼-188、镭-223 或半身放疗中的任一` —— 都在
  "既往抗肿瘤治疗史/核医学治疗记录"里查，拆成 6 条无意义 → 写进 `或条件`。
- **"除非"、"除外"、"例外"的豁免逻辑** → 写入所属条件的 `除外` 字段。
- **"包括但不限于"的列举** → 并入主条件。

### `或组` 与 `或组语义`（拆分后必填）

| 字段 | 取值 | 说明 |
|---|---|---|
| `逻辑关系` | **枚举，只允许** `单条件` / `AND` / `OR分支` | 该子条件与**同一原条号下兄弟子条件**的关系。⛔ 不得写自由文本 |
| `逻辑关系备注` | 自由文本，可空 | 跨组/跨条的关系说明（如"与 IN-10-6（胆红素）为 AND——肝功能三项均须满足"）。不参与校验 |
| `或组` | `{原条号}-OR`（多组时 `-OR1`/`-OR2`） | 同一 OR 组的分支填**同一个**值；组至少 2 个成员 |
| `或组语义` | 入选轨恒为 `任一满足即整条满足`；排除轨恒为 `任一触发即整条触发` | 两轨方向相反，写反会让整体入排结论反转 |

⛔ **`逻辑关系` 为什么必须是枚举**：自由文本会让同一个 OR 组出现两种**相反**写法，
其中的 `AND` 本指跨组关系、却被下游读成组内 AND，二选一的分支变成必须同时满足。
跨组关系照样要说清楚，只是搬到 `逻辑关系备注`。
故障档案：`references/failure-archive.md`#逻辑关系自由文本 / #and-or-误标绕过结构闸

⚠️ **两轨语义为何相反且必须显式标注**：排除项"任一分支触发即整条触发"与既有约束 17
（任一排除项 `不符合` → 建议排除）天然一致；但入选项若漏标组，约束 18
（**全部**入选 `符合` → 符合入选）会把"满足其一即可"读成"必须全部满足" ——
例如 `IN-5`（PSA 进展 **或** 软组织进展 **或** 骨病灶进展）患者只满足 PSA 一支、
另两支为「无法判断」，整体就被错判为不符合入选，**等于错误淘汰患者**。

`逻辑关系`/`或组`/`或组语义` 由 `check_track_structure.py` **闸 11** 机械校验：

| 判据 | 分级 |
|---|---|
| `逻辑关系` 取值在枚举内 | 阻断 |
| 标了 `OR分支` 必须同时有 `或组` | 阻断 |
| 组成员数 ≥2、组内 `或组语义` 一致、取值合法、与轨匹配、同组同原条号 | 阻断 |
| 某原条号下**全部**子条件标 AND 且无 `或组`，而原文含列举式 OR 连接词（`和/或`/`任一`/`以下任何`…） | 建议 |
| 多支 `或条件` 却未拆成组（≥3 支） | 建议 |

后两条只给建议：判据必有假阳（真 AND 拆分的原文也可能含 `或`，如 IN-10 血细胞条
「14天内未接受输血**或**G-CSF支持」），误阻断就白吃一轮 QC 配额。
⛔ 别把裸 `或` 当拆分判据，要看是不是**列举式**（罗列可替代的多项）。
判定侧的汇总规则见 `eligibility-judgment` 的「排除项的逻辑关系」与约束 18。

### 拆分颗粒度判定流程（逐条执行）

对每一条原文标准，按以下顺序判定颗粒度：

1. **识别连接词**：扫描 AND 类（"且/并/以及/同时/，且"）与 OR 类（"或/和或/任一/以下之一/其中之一"）。
2. **AND → 拆**：每个 AND 分支独立成子条件，各自分配子序号。
   例外：修饰同一事实的**限定性 AND**（如"有某病史 且 仍需治疗"）不拆。
   ⛔ 例外**不含**跨 `可从病例获取`、跨定性/定量两类（见 §拆分原则，一律必拆）。
3. **OR → 先判异质性再决定**：各分支需查**不同**证据位置/匹配字段 → 拆成并行子条件 + 标 `或组`/`或组语义`；
   属同一事实的等价表述/同类列举 → 写入 `或条件` 字段不拆。
4. **数值范围 → 拆上下限**：如"18-70岁" → `年龄≥18` + `年龄≤70` 两条独立子条件。
5. **主条件 + 时间窗 → 拆**：主事实条件 + 洗脱期/时间窗要求拆为两条（数值/事实条件 + 时间窗条件）。
6. **豁免/除外 → 不拆**：写入所属条件的 `除外` 字段，不单独成条。

### 颗粒度基准（一个子条件 = 一个可独立判定的事实）

判断是否已到最小颗粒度的唯一标准：**该子条件能否用一次病历字段比对得出「符合/不符合」结论**。
- 能 → 已到最小颗粒度，停止拆分。
- 不能（仍含多个彼此独立、可分别判定的事实）→ 继续拆分。

示例：`年龄18-70岁且ECOG 0-1` 含 3 个独立可判定事实 → 拆为 `年龄≥18`、`年龄≤70`、`ECOG in[0,1]` 三条子条件。

### 常见拆分错误（禁止）

- ❌ **拆分不足**：OR 的**异质替代分支**未拆（如把"活性成分过敏/辅料过敏/病史+治疗/严重过敏反应"
  塞进一条）——各分支证据位置不同，必须拆开并标 `或组`。
- ❌ **拆了不标组**：拆成并行子条件却漏 `或组`/`或组语义` —— 入选轨会被按 AND 汇总，错误淘汰患者（闸 8 阻断）。
- ❌ **过度拆分**（四种，一律并回一条）：同一事实的等价表述（单位换算、参考范围变体、同义指标
  → 写 `或条件`）；同类列举逐项拆条（锶-89/钐-153/… 都查同一份既往治疗史）；把注释/举例句
  （"影像学方法或活检确认"）从主条件剥离另立一条；语义等价的表述拆两条（"自愿参加"与
  "签署知情同意书"实为同一不可获取条件）。
- ❌ **拆分不足**：把含多个独立事实的复合句合并为一条（如"年龄且ECOG"未拆）；
  跨 `可从病例获取` 或跨定性/定量的 AND 被当成限定性 AND 留在一条内（见 §拆分原则）。
- ❌ **误拆豁免**：把"除非/除外/例外"的豁免拆成独立条件（应写入 `除外` 字段）。

### 条件ID编号规则

编号必须严格遵循以下体系，**不得自创编码模式**：

**基本格式**
- 入选标准：`IN-{原条号}-{子序号}`（如 IN-2-1, IN-2-2）
- 排除标准：`EX-{原条号}-{子序号}`（如 EX-3, EX-9-1）
- 单条无需拆分的：`IN-5`（无子序号）
- `{原条号}` 对应方案原文的入选/排除标准条目序号，`{子序号}` 从 1 起递增，反映拆分后的子条件顺序。

**子序号规则**
- 同一原条号下的子条件按原文逻辑顺序编号 1, 2, 3...，**不得跳号、不得复用**。
- 子序号用于 AND 拆分产生的独立子条件，**以及 OR 异质替代分支拆分产生的并行子条件**（后者额外标 `或组`/`或组语义`）。
- 豁免、除外、同一事实的等价表述（`或条件`）**不占子序号**——它们是同一条件内部的字段，不是独立条件。

**豁免/例外编码（禁用独立豁免编号）**
- **禁用** `EX-5-E1`、`IN-3-except` 等自创豁免编号。豁免/例外是主条件的附属，不是独立条件。
- 豁免逻辑用转化条件的"除外"字段表达：
  ```json
  { "条件ID": "EX-15", "转化条件": { "匹配字段": "INR", "运算符": "<", "阈值": "1.5×ULN", "除外": "受试者接受抗凝治疗" } }
  ```
- 即便原条目同时含主条件与豁免，也只保留**一个**条件ID，豁免写入该条的"除外"字段。

**编号连续性与唯一性**
- 每个四分类**类目是一个以 `条件ID` 为键的对象（dict）**，因此类目内条件ID 天然唯一；
  且 **dict 的 key 必须逐字等于该条目的 `条件ID` 字段**（由 `check_track_structure.py` 闸13 阻断校验）。
  条目内保留 `条件ID` 字段是为了消费方与人读方便，两者不一致会让「按 key 定位」和「按字段遍历」
  得到不同答案 —— 那就是下一个漂移源。
- 跨类目也不得重复条件ID（闸2 覆盖跨类目唯一性，不因 dict 形态而撤销）。
- 同一原条号若拆出 N 个子条件，子序号必须 1..N 连续。
- 跨四分类移动条目时，条件ID 不变（ID 锚定原条号，与分类无关）；**dict 形态下 key 随之不变**。
- ⛔ **顺序不承载任何语义**：JSON 对象在格式层面是无序的（Python 保序只是实现细节），且往 dict
  里新增条目只会落到末尾。任何需要有序展示的地方**一律由消费方按条件ID 排序**（主号数值 + 子号
  数值），禁止依赖容器内的书写顺序。
- "描述索引"按**主条件ID** 索引（一条原始标准一个键：`"IN-2": "年龄 18–70 岁，性别不限"`），
  **不是**按拆分后的子条件ID。它描述的是原始标准条款，两份 HTML 报告都按主条件ID 查它；
  ⛔ 写成 `"IN-2-1"` 这种子条件键会让报告的主条件行回退成「首个子条件的文本」，静默丢掉整条
  标准的其余部分。由 `check_track_structure.py` 闸5 双向对齐（缺键/多键都报）。
  故障档案：`references/failure-archive.md`#描述索引写成子条件键

**原条号识别规则**
- `{原条号}` 严格取自方案原文的标准条目序号（如"入选标准 2."→ 原条号 2；"排除标准（3）"→ 原条号 3）。
- 原文用字母/罗马数字/圈码编号（a/b/c、i/ii/iii、①②③）时，转为阿拉伯数字并保留层级：主条 3 下的 a/b 子项 → `IN-3-1`/`IN-3-2`。
- 原文无编号（纯段落罗列）时，按出现顺序从 1 起赋予原条号。
- 原条号一经确定即锚定原文，后续拆分/分类调整都不改变原条号。

**单条 vs 子序号的判定**
- 原条拆分后仅 1 个子条件 → 用 `IN-{原条号}`，**不加**子序号（如 `EX-9`）。
- 原条拆分后 ≥2 个子条件 → 全部加子序号 `IN-{原条号}-1..N`；**禁止**同一原条号"一个带子序号、一个不带"混用。

**编码正误对照**

| 场景 | ✅ 正确 | ❌ 错误 |
|------|--------|--------|
| 入选第2条拆出 2 个 AND 子条件 | `IN-2-1`, `IN-2-2` | `IN-2-a`, `IN-2.1` |
| 排除第5条含豁免 | `EX-5`（豁免入 `除外` 字段）| `EX-5` + `EX-5-E1` |
| 排除第9条无需拆分 | `EX-9` | `EX-9-1`（无兄弟子条件不加子序号）|
| 入选第3条含 OR **异质**替代分支 | `IN-3-1`, `IN-3-2`（各支独立成条 + 同 `或组`）| `IN-3`（把多支塞进一条）|
| 入选第4条 OR 只是**单位变体** | `IN-4`（两种写法入 `或条件` 字段）| `IN-4-1`, `IN-4-2`（同一事实拆两条）|
| 主条件 + 注释举例句 | `IN-3`（注释并入主条）| `IN-3-1` 主条 + `IN-3-2` 注释 |
| 标注子条件间关系 | `逻辑关系: "OR分支"` + `逻辑关系备注: "与 IN-10-6 为 AND"` | `逻辑关系: "AND（同组：IN-10-OR…同时与IN-10-6 AND关系）"`（自由文本，闸11 阻断）|
| OR 分支的组标记 | `逻辑关系: "OR分支"` + `或组` + `或组语义` **三者齐全** | 只写 `逻辑关系: "OR分支"` 不写 `或组`（闸11 阻断）|

## 条件转化规则

**仅对"可从病例获取"类条件执行转化**。转化目标：将自然语言描述转化为病例数据可匹配的结构化条件。

### 转化条件字段定义

```json
{
  "匹配字段": "字段名" 或 ["字段1", "字段2"],
  "运算符": "≥|≤|>|<|=|!=|in|不限",
  "阈值": 数值 或 "文字描述" 或 [离散值],
  "单位": "单位文字",
  "或条件": ["OR分支1描述", "OR分支2描述"],
  "除外": "豁免/例外条件描述" 或 ["例外1", "例外2"],
  "并列条件": "AND附加约束描述",
  "条件": "复合逻辑的文字表达",
  "适用臂": "Ib期|II期",
  "适用人群": "育龄期女性",
  "计算": "推算公式说明",
  "数据来源": "来源限定",
  "证据位置": "该条件证据通常所在的病历/检查文档或表（供判定阶段取证定位）",
  "同义词": ["病历/检查文档中可能出现的等价表述，供判定阶段按概念取证"]
}
```

**`证据位置` / `同义词`（对"可从病例获取"条件**强制**，取证线索）**：帮助下游判定阶段"按概念取证"而非"按字面取证"，并为判定后的**确定性 grep 兜底闸**（`uncertain_recheck.py`）提供关键词，避免证据存在却被判"无法判断"（历史故障：`ECOG：1分` 埋在 page5 密集段落中被漏检）。
- **硬规则**：每一条 `可从病例获取=true` 的条件，其 `转化条件` **必须**包含非空 `同义词`（≥1 个病历/检查文档侧等价表述）与 `证据位置`。**禁止**留空或省略——空缺由本轨语义 QC 标为**阻断级**问题（见 `references/criteria-qc-checklist.md`）。"不可从病例获取"条件的 `转化条件` 仍为 `null`，不要求这两个字段。
- `证据位置`：该条件证据通常所在的文档/记录类型（如检验报告单、影像/病理报告、专项评估表、病程/入院记录、既往史/用药记录）。
- `同义词`：病历/检查文档中可能出现的等价表述（缩写、别名、量化指标名、勾选项、量表分值写法等）。标准写全称而病历常写缩写时尤为关键。

示例：`{"匹配字段":["HBsAg","HBV-DNA"],"证据位置":"血清学/感染筛查报告","同义词":["乙肝表面抗原","HBV DNA","阴性","阳性"]}`

**内置同义词对照表**（高频量表/指标 + **类别→具体药名**桥接）见
**`references/synonym-table.md`** —— 填 `同义词` 时至少覆盖该表已知易漏项。
⛔ 该表与 `eligibility-judgment` 的 `uncertain_recheck.py` / `check_reason_alignment.py`
**三处必须一致**（`tests/skills/test_drug_class_synonym_consistency.py` 机械核对）。
类别→药名的桥接最易漏：标准写"仍需全身性药物治疗"，病历写"地塞米松"，不桥接下游永远对不上。
故障档案：`references/failure-archive.md`#类别与药名对不上

### 转化示例

| 原文 | 转化条件 |
|------|----------|
| "年龄18周岁以上（含）" | `{"匹配字段":"年龄","运算符":"≥","阈值":18,"单位":"周岁"}` |
| "ECOG评分0-1" | `{"匹配字段":"ECOG评分","运算符":"in","阈值":[0,1]}` |
| "ALT/AST ≤2.5×ULN 或(肝转移≤5×ULN)" | `{"匹配字段":["ALT","AST","肝转移"],"或条件":["ALT≤2.5×ULN且AST≤2.5×ULN","存在肝转移且ALT≤5×ULN且AST≤5×ULN"]}` |
| "尿蛋白≤1+ 或 24h定量<1.0g" | `{"匹配字段":["尿蛋白定性","24h尿蛋白定量"],"或条件":["尿蛋白≤1+","尿蛋白>1+且24h尿蛋白<1.0g"]}` |

### `阈值` 写"文字描述"什么时候合法（与 QC 判据对齐，⛔ 不要靠猜）

字段定义里 `"阈值": 数值 或 "文字描述" 或 [离散值]` 的"文字描述"**只在第三档合法**。
此前 SKILL 允许而 QC 清单一律判阻断，两边都没做错、配额却被烧掉两轮
（故障档案：`references/failure-archive.md`#阈值三档口径冲突）。现统一为：

| 情形 | 怎么写 | QC 分级 |
|---|---|---|
| 原文给了数值/离散值/区间 | 结构化数值 + 标准 `运算符`（`≥ ≤ > < = != in ∈ 不限`）| ① 通过 |
| 原文**自带**判定要件，只是写成一句自然语言 | 必须收敛成结构化字段，⛔ 不得原样抄 | ② **阻断级**，本轮修 |
| 判定要件写在**外部评价标准**里（PCWG3 / RECIST V1.1 / iRECIST / CTCAE / NYHA / Child-Pugh…），或本质是相对比较（「与上次骨扫描相比」）| 保留文字描述 + **备注写明依赖哪个标准、缺什么** | ③ `upstream_issues`，首轮归档、不占阻断额度 |

解析阶段能做的：命中第三档时**主动在备注写清依赖的标准名与缺失要件**，QC 首轮就能定档。
判据与主代理处置见 `references/criteria-qc-checklist.md` 的「阈值/运算符可执行性：三档判据」；
`check_track_structure.py` **闸 12** 会把非标准 `运算符` 的条目一次性点名并回报命中的标准名
（建议级）。

## 日期维度规则

涉及时间窗判断的条件**必须**标注完整的日期维度：

```json
{
  "事件": "什么事件/检查/治疗",
  "发生日期": {
    "来源": "病例提取",
    "字段": "具体字段名",
    "默认值": null
  },
  "参考事件": "知情同意书签署|筛选|入组|首次给药|检测|末次用药|手术|随机化",
  "参考日期": {
    "来源": "病例提取，缺失则默认判定当天",
    "字段": "具体字段名",
    "默认值": "判定当天"
  },
  "时间窗": "N周|N个月|N年",
  "判断": "逻辑表达式（如：事件发生日期 落在 [参考日期-时间窗, 参考日期] 区间内）"
}
```

⛔ **`参考事件` 必须照标准原文抄，不得统一压成「筛选」**。标准写「**签署知情同意书**前 6 个月内
接受过锶-89…」，基准就是 ICF 签署日；写「**首次给药**前 4 周内」就是首次给药日。这两个日期在
真实病历里可能相差数周到数月，基准错位会让整条时间窗判断偏移，而**判定阶段看不出来**——
判定子代理只拿到 `日期维度`，它没有方案原文可以复核基准。`参考事件` 是判定侧取证的唯一线索。

`参考事件` 不在上面枚举里时，**照原文补充**（如「末次放疗」「造血干细胞移植」），不要就近取整
成枚举里的某一个。枚举是常见值清单，不是封闭集合。

**日期处理原则**：
- 可从病例提取的日期 → 优先提取
- **参考日期取证优先级**：① 病历里该 `参考事件` 的明确日期（如「知情同意书签署=2026-04-15 16:21」）
  → ② 取不到才用**判定当天**兜底。判定当天由判定阶段的主代理注入，解析阶段只需把
  `默认值` 标为 `"判定当天"`，⛔ 不要在解析产物里写死某个具体日期
- 既往事件的日期（手术/用药/诊断）→ 从病例既往史提取
- 时间窗判断增加子提取维度：事件 + 发生日期
- `参考日期.字段` 要写**病历里可检索的字段名**（「知情同意书签署日期」而非「基线日期」），
  它直接决定判定侧能不能找到这个日期

## 可获取性判定标准

### 可从病例获取
- 确诊诊断（组织学/细胞学/影像学）
- 疾病分期（TNM/临床分期）
- 实验室检验值（血常规/生化/凝血/感染标志物）
- 影像学发现（转移/侵犯/病灶大小）
- 用药史（既往治疗方案/用药时间）
- 手术史（手术类型/日期）
- 体格检查（ECOG评分/生命体征）
- 基因检测结果（突变状态）
- 过敏史、合并症
- 妊娠/哺乳状态

### 不可从病例获取
- 知情同意（签署ICF、自愿参加）
- 受试者承诺（避孕承诺、依从性承诺）
- 预后预估（预期生存时间）
- 未来计划（预期研究期间的手术/用药安排）
- 研究者主观评估（"研究者认为..."、"经评估适合..."）

> ⚠️ **该分类是"检索优先级的先验提示"，不是"下游免检许可"**。它只表示这类条件**通常**不在
> 病历里，**不表示判定阶段可以不查病历**。实践中这些事实常有客观痕迹：知情同意有签署时间与
> 知情过程记录、承诺类有筛选期访谈记录、预后类有病程评估结论、主观评估类有"研究者认为…"的原话。
>
> 判定侧的对应规则见 `eligibility-judgment` 的「原则七之前：从严判断」B 与约束 16；
> 故障档案：`references/failure-archive.md`#分类被读成免检许可
>
> 本分类**唯一**的下游作用：`转化条件` 可为 `null`（不强制 `同义词`/`证据位置`）。
> 判定阶段仍会由 `uncertain_recheck.py` 从 `子条件`/`原文` 派生关键词做机械反查，
> 因此**请把 `子条件` 写成含具体名词的可检索表述**（如"自愿参加临床试验并签署知情同意书"
> 而非"研究者判断"），否则反查派生不出关键词、只能标 `no_keywords` 交人工。

## 输出格式

**双轨解析**：入选轨与排除轨各产出一份文件，只含本轨内容；全量包由
`parse_pack.py assemble` 合成（详见 `references/parse-delegation.md`）。

| 文件 | 由谁产出 | 内容 |
|------|---------|------|
| `workspace/criteria_meta.json` | `方案元数据` 手写；其余由 `locate_criteria_sections.py` 落盘 | `方案元数据` + `段行号`（splitlines 坐标）+ `末条号`（源声明值）+ `补充章节` + `行号坐标系` |
| `workspace/criteria_parsed_IN.json` | IN 轨解析子代理 | `四分类.入选_*` 两个类目 + `描述索引`（`IN-*`） |
| `workspace/criteria_parsed_EX.json` | EX 轨解析子代理 | `四分类.排除_*` 两个类目 + `描述索引`（`EX-*`） |
| `workspace/criteria_qc_{IN,EX}.json` | QC 子代理 | 该轨 QC 结论（`passed` / `blocking_issues` / `residual_issues`）|
| `workspace/criteria_structure_baseline_{IN,EX}.json` | `check_track_structure.py --snapshot` | 修订前基线快照（中间产物，不交付）|
| `workspace/criteria_judge_{IN,EX}.json` | `parse_pack.py slim` | 该轨判定输入包（剔除非判定字段，体积约半） |
| `workspace/criteria_parsed.json` | `parse_pack.py assemble` | 全量包（下方顶层结构），报告与全量终检的输入 |
| `outputs/criteria_parsed.json` | 主代理拷贝 | 最终交付物 |

完整 schema 参见 `/mnt/skills/custom/criteria-parser/references/schema_example.json`。

**全量包顶层结构**（assemble 产物；单轨文件只含其中 `四分类` 的本轨类目与 `描述索引`）：
```json
{
  "方案元数据": { "方案编号", "方案标题", "试验药品", "版本", "版本日期", "来源", "分期臂" },
  "解析说明": { "四分类", "拆分原则", "日期处理", "条件转化", "可获取性判定" },
  "四分类": {
    "入选_可从病例获取": {
      "IN-2-1": { "条件ID": "IN-2-1", "来源标准", "原文", "子条件", "逻辑关系", "逻辑关系备注", "或组", "或组语义", "可从病例获取", "转化条件", "日期维度", "备注" },
      "IN-2-2": { "条件ID": "IN-2-2", "...": "..." }
    },
    "入选_不可从病例获取": { "IN-1-1": { "条件ID": "IN-1-1", "...": "..." } },
    "排除_可从病例获取": { "EX-1-1": { "条件ID": "EX-1-1", "...": "..." } },
    "排除_不可从病例获取": { "EX-20": { "条件ID": "EX-20", "...": "..." } }
  },
  "汇总统计": { "入选_可从病例获取", "入选_不可从病例获取", "排除_可从病例获取", "排除_不可从病例获取", "子条件总数" },
  "描述索引": { "IN-1": "短描述", "EX-1": "短描述" }   // 按主条件ID（一条原始标准一个键）
}
```

⛔ **类目是对象（dict）不是数组**，key = 该条目的 `条件ID`（与条目内的 `条件ID` 字段一致）。
这样 `apply_json_patches` 的 pointer 就是 `/四分类/{类目}/{条件ID}/转化条件/阈值` —— 按身份定位，
命中即命中、不命中即报错。**历史原因（thread `3a745b38`）**：类目原本是数组，pointer 只能用数字
下标；一次 `add /21` 之后**跨调用**沿用旧下标，24 笔单字段写入全部落到前一条条目上（乙肝阈值写进
CNS 转移条目），27 次调用全返回 `OK` 无一报错，两轮 QC 白烧，最终撞 `recursion_limit=420`。
数字下标只要在界内就一定"成功"，写对与写错在工具层同形，因此既不报错也不留痕。

⛔ **单轨文件不得产出** `方案元数据` / `解析说明` / `汇总统计`：前者是全篇级（两轨都写会冲突），
中者是常量样板，后者必须由 assemble 按实际条目数**重算**（不信任任一轨自报的数字）。


**本轨边界（硬规则）**：

- IN 轨只读入选段、只产 `IN-*` 条目、只写 `入选_*` 两个类目；EX 轨对称。
  越界会被 `parse_pack.py slim` 的单轨结构闸阻断（故障档案：`references/failure-archive.md`#越界写进另一轨）。
- **禁止读原始方案文档**：`uploads/` 下的入排标准/方案原始文档（`.docx`/`.pdf`/`.md`）
  **禁止** `parse_document` 或 `read_file`——内容已逐字进入 `eligibility_criteria_raw.md`，
  再解析属重复（故障档案：`references/failure-archive.md`#重复解析原始文档）。缺条应报告条号由主代理补提取。
- ⛔ **解析子代理落盘后必须自跑结构闸到 `exit 0` 才返回**，且解析时就照 5 条结构规则速查写
  （条件ID 唯一+前缀一致 / 子序号不混用且连续 / `描述索引` 与实体双向对应 / 原条号全覆盖 /
  `原文` 在 raw.md 中逐字可查）——规则与命令见 `references/parse-delegation.md`。
  把结构收敛留给主代理去发现，代价是整轨重做一个子任务（故障档案：`references/failure-archive.md`#结构收敛留给主代理）。

**每轨的解析内容**：

1. 逐条拆分本轨标准为最小子颗粒度（AND 拆、OR 不拆、豁免入 `除外` 字段）
2. 判定每条的可获取性
3. 对"可从病例获取"类条目填写 `转化条件`（**含非空 `同义词` 与 `证据位置`，硬规则**）和 `日期维度`
4. "不可从病例获取"类条目的 `转化条件` 和 `日期维度` 填 `null`
5. 产出本轨 `描述索引`（键为本轨前缀的条件ID）

### ⚠️ 输出必须分片写入（硬规则，禁止单次全量 write_file）

> **适用范围：仅限本节所述的「解析阶段新建本轨文件」。**
> 文件建好之后的 **QC 后修订**走相反规则——只允许 `apply_json_patches` 的对象级形态、
> 禁止 `write_file` 与 `str_replace`，见下方「QC 后修订」与 `references/criteria-repair.md`。
>
> ⛔ 两种情形都**禁止用 `bash` 内联脚本**（`python3 -c`、heredoc、`echo >`）生成或改写 `.json`。
> 见 `references/failure-archive.md`「内联脚本生成 JSON」。

单个方案的子条件常达 40–60 条（单轨约 20–30 条），每条又含
`转化条件`/`同义词`/`证据位置`/`日期维度` 等富字段。一次性把完整 JSON 作为**单个**
`write_file` 参数生成会导致该轮 LLM 调用生成时长过长（数万 token 无中间进度信号），
触发子代理 inactivity 看门狗（默认 300s）而中断失败（故障档案：`references/failure-archive.md`#单次全量写入触发看门狗）。
因此**必须**按下述节奏分批 `write_file`：

1. **第一批**（`write_file`，新建文件）：`{`、开写 `四分类` 的本轨第一个类目对象的前一批条目。
2. **后续批**（`write_file` 且 `append=True`）：每批追加 **10–15 条**子条件，
   逐个填充本轨的两个类目（可从病例获取 → 不可从病例获取）。
   每条的写法是 `"{条件ID}": { "条件ID": "{条件ID}", ... }`（key 与字段同值）。
3. **最后一批**（`write_file` 且 `append=True`）：闭合 `四分类`，追加本轨 `描述索引`，
   并写入结尾 `}`。
4. 每批写入后再进行下一批，使每次工具调用都产生一个执行进度信号（super-step），
   既避免单轮生成超时，也让 JSON 分段落盘、便于中断后续跑续写。

**颗粒度**：每次 `write_file(append=True)` 追加不超过 ~15 条子条件。条目越多，批次越多，
但**严禁**把全部条目塞进一次 write_file。追加时注意 JSON 语法：仅在最后一批闭合括号，
中间批次保持对象处于可续写状态（可先在草稿中排布好整体结构，再分段输出对应文本片段）。
