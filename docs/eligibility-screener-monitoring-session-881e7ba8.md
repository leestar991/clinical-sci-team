## 问题一:IN 轨 QC 不收敛(R1 12 条 → R2 11 条 → R3 仍 11 条)

### 表层形态

| 轮 | blocking | 条目 | entity digest |
|---|---|---|---|
| R1 | 12 | IN-3-1/3-2/3-3、IN-4-1/4-2、IN-5、IN-7-2、IN-10-5/6/7/9、IN-11-1 | — |
| R2 | 11 | 与 R1 高度重叠(7 条同 ID)+ 4 条 late_discovery(IN-4-3、IN-10-8/10-10、IN-7-3) | **全部变化** |

全部阻断同一类型:**「转化条件不可执行」**(阻断级)。条目形态高度一致:

```jsonc
"转化条件": {
  "匹配字段": ["病理诊断", "细胞学诊断"],
  "运算符": "不限",          // ← 结构化缺席
  "阈值": null,
  "或条件": ["病理诊断证实转移性结直肠癌", "细胞学诊断证实转移性结直肠癌"]  // ← OR 装在文本里
}
// 或 "条件": "无肝转移且ALT≤2.5×ULN且AST≤2.5×ULN"  ← AND 装在文本里(IN-10-8)
```

对照**通过**的条目(IN-10-1/10-2):单要件 + `运算符:≥` + `阈值:1.5` —— 多要件并列在现 schema 下的
唯一合法表达是**拆成并行子条件**(如 IN-4-2/4-3、EX-9-1..5 那样 + `或组`),但这层等价关系没被说破。

### 根因:指令-能力脱节的拉锯

1. **QC 的 action 是描述性的,不是可执行指令**:「收敛为可执行 OR/AND 结构」需要的操作是
   **拆条目手术**(一条拆多条 + 标或组 + 编号),而 `criteria-repair.md` 修订模板教的是
   「按 QC 点名单条修复」(str_replace/patch 单字段),没有拆分操作指引与样例。
2. **修订子代理每轮只做它会的:改措辞**。QC finding 自述暴露了这一点——「较上一轮去除了
   误导性或条件」「语义方向正确」「已保留正确语义说明」——每轮 entity digest 全变
   (确实在改),但 `运算符=不限/阈值=null/文本承载 AND/OR` 的结构纹丝不动;QC 按同判据再拦。
3. **修订成本失控**:3 个 IN 修订任务(34/35/45 步)≈2.6M token,同判据拉锯 3 轮无熔断,
   R2 还在「晚发现」新条目(全量复查纪律的代价面)。

### QC 的失守(EX R1-R3)

- R1/R2 点了 EX-3/7/10/13/17,但点的全是**引文追溯/版式注释**问题;**拆分不足(清单明文
  阻断级)只有 EX-9 被点**——QC 的火力被机械预判(逐字查不到)带偏。
- R3 报告**自相矛盾**:`passed=true` + blocking 6 条,其中:
  - EX-3/EX-7:status=`fixed`,action 自述「如后续做可执行性增强,**可考虑**按 a-d 分支拆…」
    「可后续考虑拆成 OR 分支,**但不构成阻断**」——**把清单里阻断级的『应拆未拆』判据私自降档**;
  - EX-10/EX-17:status=`open`(真阻断仍在)——passed=true 与 open 并存;
  - EX-13:status=`upstream` 塞在 blocking_issues 里。
- **兜底有效**:`judge_pack._qc_passed` 三重校验(passed + **open blocking 非空** + 覆盖率),
  EX-10/17 的 open 会让 slim QC 闸拦截切包——不会污染判定,但会话停在 P2 等用户。

## 优化方案

### P0-1 ✅ 已落地(commit eb2ad8e9,2026-08-26)

按「拆分规则已在 parsing-rules.md,repair 只需指回」的思路落地:QC 第二档禁笼统 type,
必须报四子类型(拆分不充分/与或逻辑错误/证据定位缺失/字段不可执行)且 action 写具体操作
指向 parsing-rules.md §拆分原则;repair 处置手册补「拆分不充分」行(改措辞不构成修复)。
原方案节(新写拆分指引)作废——规则不复制,只指回:

`criteria-repair.md` 新增一节:**多要件文本承载(运算符=不限+条件/或条件装判定)的修复 =
拆成并行子条件并标 `或组`**,给最小操作序列(条件ID 重编号、或组命名、`描述索引` 同步、
结构闸复跑)与前后对照样例;同时 QC 检查单的 action 模板标准化:该类 finding 的 action
**必须**是「拆分为 {轨}-{条}-{N}.. 并标或组 {X}-OR」,⛔ 禁止「改善表达/收敛为可执行结构」
这类不可执行措辞。

### P0-2 ✅ 已落地(commit 1b53b1b8,2026-08-26)

- BashWritePolicyMiddleware 新增删除/改名分支(rm/unlink/shred/mv 指向治理产物 → 拒绝,
  inline os.remove 同拦):删除治理产物 = 连 read-before-write 读标记一并销毁,后续
  write_file 零闸阻拦。35 项真实命令语料测试(TDD),bash 相关测试面 371 passed。
- parse-delegation.md 补「重做 = 在现有产物上修订,禁 rm/重建」铁律(881e7ba8 叙事入档)。
- 治理产物重做只动点名条目——与判定域「结构闸不过=回派重判,禁转码」同构。
- 重做任务的输入瘦身:规则/schema 不由子代理自读(前 4 步 ~200k token),学判定域
  `render_judge_prompt`(机械渲染 prompt_file)模式前置注入。

### P1 QC 报告形态闸加固

- `criteria-qc-checklist.md` 措辞加固:⛔「应拆未拆」等阻断级判据**不得**以「可考虑/不构成
  阻断/维持当前表达」降档,降档 = 自我放行;
- QC 报告模板:修复确认的条目(status=fixed)挪出 `blocking_issues`(放 residual/notes),
  `blocking_issues` 只允许 open;upstream 只进 `upstream_issues`;
- (可选)`_self_release_evidence` 增加检测:blocking 条目里 status=fixed 且 action 含
  「可考虑/不构成阻断」→ 列为自我放行痕迹。

### P2 修订收敛熔断

修订任务自检加一条:**action 要求「结构化/拆分」的条目,产物 diff 里必须出现
新增条目ID 或 `运算符`/`阈值` 字段变化**,否则禁止结束任务(digest 变了≠修对了)。

## 效果预估

- IN 类不收敛:R2 即可闭合(修订第一次就做拆分手术),省 2 轮 QC + 2 个修订任务 ≈ 2M token / ~15 min;
- EX 类倒退:拆分版不被 rm,重做只修闸 9 引文 → 30 步字符级空转大半可省,~0.8M token / ~5 min。
