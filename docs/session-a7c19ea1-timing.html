最大单点浪费

一个在构造上无法成功的循环

S1 · 750 秒 / 1.59M token / 零产出

17:50:58 – 18:02:29，lead 用 17 次调用反复试图把 OCR 来源标注里的宿主路径改成虚拟路径。这个循环永远不可能收敛，因为读写两端做了方向相反的路径翻译：

写入 · LocalSandbox.write_file → _resolve_paths_in_content() 把 /mnt/… 正向翻译成宿主路径落盘 读出 · LocalSandbox.read_file 对 _agent_written_paths 内的文件 _reverse_resolve_paths_in_output()，把宿主路径反向翻译回 /mnt/… 结果 · read_file 显示「已修好」，bash grep 走真实磁盘显示「没修好」——每一次校验都和每一次写入互相矛盾

agent 在 17:59:19 自己得出了正确结论（「write_file 会静默翻译」），但仍无法让磁盘留下 /mnt。磁盘实测证实：39/39 页 OCR 与聚合后的 ocr_records.md（13 + 26 行）全部是 /Users 前缀，/mnt 计数为 0。

值得注意的是，parse_image_batch 的 _provenance_line() 注释明确写着 “Virtual path only. Host absolute paths break on any other deployment.”——工具的意图是对的，是底层 sandbox 的内容翻译把它推翻了。

修复方向：provenance 这类「内容即数据、不是可执行路径」的写入应绕过 _resolve_paths_in_content；或让反向解析不再限定 _agent_written_paths，使读写对称。当前的不对称意味着 agent 永远看不到磁盘真相，任何同类问题都会重演。

S2 · 闸循环：单任务 28 次执行

check_track_structure.py 全程 执行 51 次，其中 28 次集中在那个 901 秒的 EX 轨修订任务里，形成「改一条 → 跑全闸」的往返节奏（编辑 10 次、闸 28 次）。另有 20 次是用 sed/grep 读闸的源码去猜它想要什么，加 11 次 read_file 该脚本——这说明闸的报错没有把「要什么」说清楚，子代理只能反向工程。

这两类必须分开统计：analyze_eligibility_run.py 报的 gate_script_calls=56 把执行和读源码混为一谈，掩盖了「规格不清」这个独立问题。

S3 · 产物闸 2 次 failed，但重试有效

首轮双轨解析都因 required outputs missing/empty 被拦（缺 criteria_parsed_IN.json / _EX.json），重试全部成功。代价是 452 秒和 43 万 token 的返工，但闸的判断是对的，报错也列出了目标目录的实际文件名——这是相比历史会话的明确改善。

如何结束

用户主动中断，不是崩溃

18:16:25 收到 cancel(action=interrupt)，两个判定子代理被 Requested cancellation 逐个取消，run 于 18:17:25 落 interrupted。3 条 run.error 均为 CancelledError，是取消的正常传播。因此两个判定任务没有终态 usage，subagent_tokens_from_tasks（733 万）低于 run 行的 951 万——这个差额是中断造成的，不是漏账。

数据源：Postgres runs / run_events（只读）+ logs/gateway.log；无重放、无模型调用。 子代理延迟无埋点，其耗时为 5 秒分辨率的轮询推算；判定阶段两任务的 token 因中断缺失。
